## Extracted Core Loop

**Scout → field → resolve round-by-round → get paid (XP + coins) → repair/restock → re-queue.**

In one breath: **pick/fix your 6 → start a battle → click through rounds watching types/moves/PP decide → collect XP + coins → heal/buy → fight again with a slightly stronger team.**

Why it has pull (when it works): each cycle changes persistent state (levels, evolutions, wallet, inventory, history/rank) and promises a slightly different next fight (opponent band derived from team average level per README seeds/J3; deterministic move choice + type/STAB/PP/Struggle per RF-15 gives readable cause-effect). Fantasy: "my team gets stronger and richer each fight."

## Loop Drivers

- **Progression fantasy (strongest pull):** XP → level → stats scale → evolution → new moves. Every fight moves numbers forward; loss still pays (XP + 40 coins), so the loop never fully stalls.
- **Readable mastery:** deterministic best-move choice (max expected damage), type chart ×2/×0.5/×0 + STAB ×1.5, Speed order, PP/Struggle. Player can explain win/loss (PRODUCT "jogador entende por que venceu/perdeu").
- **Novelty per confrontation:** opponent re-rolled each new battle within a level band (post-0049 fix; pre-fix same-opponent bug killed this driver entirely).
- **Collection/tinkering (support):** slots, 4-move selection from full movelist, held/consumable items. Amplifies the loop for tinkerers; decorates it for casuals.
- **Retention wrapper (weak):** history/rank (local wins + global leaders). Compares past selves/others; does not change next fight.

## Loop Breaks and Dead Steps

1. **Resolve step is a chore treadmill (structural, motivation-killing).** One HTTP round-trip + one click per round (`POST /battle/play`) stretches the emotional peak across N clicks with identical interaction. Backlog itself proposes the fix ("batalhar resolve a batalha inteira — fim das rodadas manuais", REQUIREMENTS limitation note). Long chain ≠ loop: the cycle feels cyclical only at battle granularity, flat at round granularity.
2. **Heal tax is a mandatory detour, not a decision (friction, trust-adjacent).** Fainted lock (cannot remove until cured, 0064) + paid heal forces Center visit after hard fights. No triage choice (which member, partial vs full heal strategy) is visible in docs — it reads as toll booth between meaningful beats, the classic bloated transition step.
3. **Losing pays almost as well as drawing (tension leak).** `lose 40 / draw 50 / win 100`: defeat costs only 10 coins vs a draw and still grants XP, while opponents stay level 1 (species band only, README:70-71). Consequence is weak, escalation is species-swap wallpaper rather than power escalation — risk of emotionally flat loop where re-entry reason is "numbers go up" rather than "I must adapt."
4. **Setup masquerades as loop (false-loop risk).** Team assembly (cap 6, no duplicates, slot reorder, move picking) is one-time setup + occasional tinkering, not recurrence. Docs sometimes frame it as the loop's first beat; per skill rules, if optional layers vanished the minute-to-minute engine would still be **battle → reward → repair → battle**. Treating setup as core invites feature sprawl (more filters, more manage screens) instead of tightening resolve/reward.
5. **Support systems compete with the core (bloat watch, not must-fix).** Move management page, Mart stones rotation, item assign/hold/restore-on-remove (0052), journey gate, search hints for non-base forms — each is reasonable alone, but together they lengthen time-between-battles. Assumption (not playtested): if re-queue takes >2 navigations after rewards, the motivational circuit cools before closing.

## Design Implications

1. **Issue:** round-per-click resolve dilutes the payoff. **Cause:** incremental `play_round` API exposed 1:1 as UI (RF-13), preserving engine purity at the cost of pacing. **Change:** keep `play_round` in domain, add "Resolver batalha" (full-run to `finished?`) as primary button, keep "Jogar rodada" as secondary/skip. **Expected effect:** one decision → one payoff; loop length matches attention span; round log becomes replay, not toll.
   - *Tradeoff:* fewer pageviews/clicks per battle; less suspense-per-round. Mitigate with staggered log reveal (already have `--log-delay`) on the resolved result.
2. **Issue:** heal toll booth. **Cause:** fainted-lock + paid full heal with no interesting choice. **Change:** make repair a decision: show per-member heal cost preview + "heal all / heal cheap (revive to 1 HP?) / skip and fight weakened" if rules allow; at minimum collapse heal into the post-battle screen (one click, cost shown). **Expected effect:** transition step shortens; player agency returns to the weakest beat.
   - *If removal answers "cut or simplify":* cut the fainted-removal block OR cut the heal fee for the losing side — one gate per beat, not two.
3. **Issue:** weak defeat consequence + flat escalation. **Cause:** lose-pays-40 + level-1 opponents make losing a slightly slower win. **Change (smallest):** scale rewards with band/difficulty or streak (e.g., beat higher band = bonus; lose = XP only, no coins — needs SDD session, do not hotfix economy). **Expected effect:** renewed tension: picking the next fight matters, losing stings enough to adapt team/moves/items.
4. **Separate (do not merge):** core = battle→reward→repair→battle; progression (XP/evo), economy (wallet/Mart), tinkering (moves/items/slots), retention (history/rank) are support. **Change:** evaluate every new feature by "does it shorten or enrich time-to-next-battle?" Filters beyond name search, stone price dynamics, move-learn-level display (all in backlog) decorate; resolve-button + post-battle heal-in-one-click strengthen. **Expected effect:** stops sprawl from starving the engine.

## Minimal Loop Fix

Add **"Resolver batalha" (resolve-to-finish) as the primary battle button** reusing the existing incremental engine in a loop (no domain change), leaving per-round play as secondary. Single change, no schema/migration: shortest path from chore-treadmill to closed motivational circuit — every other fix (heal-in-place, reward scaling) amplifies this one but none substitutes for it.
